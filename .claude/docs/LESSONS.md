# Lessons

- **S1 (2026-11-21):** the plan's file paths (`minotaurus/levels.py`) disagreed with CLAUDE.md
  (`minotaurus/engine/`). CLAUDE.md wins; fix the plan when next edited.
- **S1:** tests that pin the exact observation layout protect `obs_version` 1; a layout change must
  bump the version.
- **S1:** the race rule "does the loser keep going?" was not in the design; chosen: the race ends at
  the first finish.
- **Web setup (2026-11-21):** `@vitejs/plugin-react` 6 needs Vite 8; with Vite 7 use plugin-react 5.
- **Dev check:** stop a started `minotaurus dev` with `timeout -s INT` (Ctrl-C path), not `pkill`; the
  Ctrl-C path shuts down both child processes.
- **S4 (2026-11-21):** build the page against a written message contract plus a mock; the server
  (S3) then implements the contract and its tests validate against `messages.schema.json`.
- **S4:** logic in pure modules (reducer, history, parser) keeps it testable with `bun test`.
- **Web style (2026-11-21):** for any UI work, load the `design-taste-frontend` skill first (app-screen
  run) and keep reusable pieces in `web/src/components/`; pages only compose them.
- **Inspector:** set `CHROME_PATH` to Playwright's Chromium (`~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome`).
- **S2 (2026-11-22):** a 77-number observation cannot be packed into one int64 as bits. Use a
  hashed key (`sum((obs + 1) * weight)`) computed identically in Python and in the ONNX graph.
- **S2:** onnxruntime int64 `ReduceSum` is exact only up to 2**53; keep integer keys below that,
  or Python and ONNX disagree. Always test "ONNX output equals in-memory brain".
- **S2:** torch CPU wheels: use an `explicit = true` uv index plus `[tool.uv.sources]` so numpy and
  other packages still come from PyPI. Export with `torch.onnx.export(..., dynamo=False)` to avoid
  the onnxscript dependency.
- **Code style (2026-11-22, CEO rule):** no promise chaining; use `async`/`await` with `try`/`catch` everywhere. Rule is in CLAUDE.md, the agent brief and agent memory.
- **Mock (2026-11-22, CEO decision):** the page has no mock code at all. A fake arena is a Vite plugin (`web/mock/arenaMock.ts`, mode `mock`: `bun run dev:mock`, `minotaurus dev --mock`) that serves the same contract (`/api/levels`, `/api/brain`, `WS /ws/run`) with a hand-written WebSocket handshake (no `ws` dependency). Delete `web/mock/` when S3 lands.
- **ApiService + zod (2026-11-22, CEO rule):** one `ApiService` class is the only place that fetches or opens a socket; zod schemas in `protocol.ts` validate every reply and WebSocket frame. `data/schemas/message-samples.json` is checked by pytest (JSON Schema) and bun (zod), so the two sides cannot drift. `ApiService` takes `fetchFn` and `openSocket` so tests use fakes.
- **Folders (2026-11-22, CEO rule):** services (`ApiService`, attempt `history`) live in `web/src/services/`, components in `web/src/components/`.
- **Endpoint files (2026-11-22, CEO rule):** `ApiService` is the generic core (get, post, socket, validation, errors); each endpoint is one file in `web/src/services/endpoints/` (`levels`, `brain`, `run`); `services/index.ts` re-exports the endpoint functions.
- **No service props (2026-11-22, CEO rule):** endpoint functions use the shared `apiService` themselves; components call `getLevels()`, `uploadBrain(file)`, `openRun(id, cb)` and pass only their own arguments. Endpoint tests stub the globals (`fetch`, `WebSocket`, `location`).
- **CLI (2026-11-22, CEO decision):** `minotaurus/cli/` uses Typer: one file per command with one typed function `run`; `__init__.py` registers them on `app`. Entry point `minotaurus = "minotaurus.cli:main"`. Tests use `typer.testing.CliRunner`. Dependency added: `typer`. A top-level `cli/` was tried and reverted: the name is too generic and code belongs inside the package.
- **Pydantic (2026-11-22, CEO rule):** the training config is Pydantic models in `minotaurus/trainer/config.py` (strict, `extra=forbid`); `jsonschema` stays only for level files. The brain-config JSON Schema file is generated from the models. S3's server messages will be Pydantic models too, checked against `message-samples.json`.
- **Lean Pydantic (2026-11-22):** no wrapper layers around a model: no custom error class, no dataclass forwarding properties, no message reshaping. Use `Model.model_validate(_json)` and let `ValidationError` speak (it lists every wrong setting at once). Put small helpers on the model (`resolve_levels()`, `params`). Typer's `exists=True` handles a missing file.
- **Plain code (2026-11-22, CEO rule):** no compact comprehensions or one-line tricks; explicit loops with named steps. Applied to the level functions; older code is fixed when it is touched.
- **S3 server (2026-11-22):** messages are Pydantic models checked against the shared samples; the run loop is an async generator (`run_arena`), no callbacks; one-run flag reset in `try/finally`; errors reach the page as `{"message": ...}`. FastAPI uploads need `python-multipart` and WebSocket needs `websockets`. Never delete a file without the CEO's go (a test file was deleted and restored).
- **Animation and charts (2026-11-22):** keep the maths in pure functions (`stepPieces`, `layoutLine`) with bun tests; the canvas and SVG are thin. No library for confetti or charts. Respect `prefers-reduced-motion`. A static render plus headless Chrome screenshot checks a chart when nothing can click.
- **Thin maze walls (2026-11-22, CEO request):** the grid stays blocks in the data; the page draws each wall cell as a point and joins touching wall cells with one thin line (`wallLines`, pure and tested). A gap in the outer wall stays a gap. Works for any grid, not only room-and-wall mazes.
- **More levels (2026-11-22, CEO request):** five perfect mazes made with a one-off depth-first script (not in the repo, G1 is the real generator); the seed with the longest shortest path was kept per size. `load_all_levels` orders easy, medium, hard, then id, and a test checks each shipped level has a longer shortest path than the one before. A brain trained on easy-01 does not solve the new levels: it memorised one maze (see G1).
- **Maze generator (2026-11-23, G1):** pools are drawn test first, then validation, then train, each skipping any layout already used, so no train maze is a test maze. The pool settings go into the `.onnx` metadata and scoring refuses a brain whose settings differ from the config. Size 7 has too few different mazes for 16 pools: ask for less or a bigger size (the code says so). Result with a Q-table, size 9, 50 train mazes, 6000 episodes: train 92%, validation 0%, test 0%. It memorises; a Q-table on raw 5x5 views does not generalise yet.
- **Generator follow-up (2026-11-23):** compare mazes by their walls, not their grid, once the start
  can move: 5 x 5 has 2 wall layouts but 14 grids. An unseen view gives the Q-table brain four
  zero scores and `argmax` turns that into "up" every time (61 to 71% of held-out steps).
- **Best brain on validation (2026-11-23, G4):** a DQN can collapse in its last few hundred tries, so
  the last brain is not the best. Check on validation at fixed steps and at the end, keep a copy of
  the best (a tie keeps the later one, so an untrained early brain never wins a 0% tie), and say
  which episode was exported. Keep `scores.json` stable; new facts go in `metrics.jsonl` and metadata.
- **DQN research (2026-11-23, R1):** on made mazes the exit is too rare to find by chance, so plain
  DQN learns only "do not bump"; check a random walk's success within the step limit before tuning.
  Potential-based shaping (walking distance to the exit) fixed size 9. Report mean and spread over
  several seeds: three seeds hid both the collapse risk and the size of the Enb effect. A brain
  without memory fails by looping, which a little seeded randomness when playing breaks.
- **Timing checks (2026-11-23):** a per-call time limit must not time the first call of a new
  onnxruntime session (cold start); it made a valid brain fail now and then.
- **L1 (2026-11-24):** a breaking change inside a version can keep old brains working when the
  new value equals the old one in the common case (visited once = 1.0); measure old brains before
  and after, here they even improved (a bump now changes the input).
- **L1:** the Q-table key needs the same change in Python and in the ONNX graph; with a fixed
  operator allowlist, min(x, 1) is x - Relu(x - 1).
- **L1:** `cmd | tail -1 && git commit` commits even when the tests fail (the pipe returns tail's
  status); use `set -o pipefail` or check the test exit code before committing.
- **obs_version exception (2026-11-24):** the visited layer became a visit count inside version 1; the CEO confirmed it because the arena is local. Revisit before P1 (online race): bump to version 2 then.
- **G2 (2026-11-24):** before building, grep what a teammate already added; Mo's work had neither the path ratio nor the parameter count, so G2 only extended `train.py`, `export.py`, `Result` and its twins. A new optional field in a message needs the Pydantic model, the zod schema, `messages.schema.json` and the shared samples together. A Q-table's parameters are 4 per table row, so the number grows while it trains.
- **Several seeds (2026-11-24, G6):** one run is one process on one core, so a process pool (spawn) runs seeds side by side; a generator yields each result as it ends (no callbacks). The best seed is picked on validation, never test. Keep `matplotlib` imports out of the CLI's top level: every command would pay for them. Parallel runs of 3.5 s each took 9 s together, mostly process start-up, so seeds only pay off for longer runs.
- **Mixed sizes (2026-11-24, G7):** a brain trained on one maze size (9x9, exit inside) scored 84% on its test pile but finished 1 of 6 hand-made levels (sizes 9 to 21, exit in the wall). A test pile only measures what it was drawn from, so keep an unrelated check (the hand-made levels) next to it. `sizes` splits each pile evenly and interleaves the sizes; it cannot be combined with `stages`.
- **Test mazes and impossible (2026-11-24, G8):** keep the saved test mazes out of `load_all_levels` (a config picking `difficulty` would train on them); the portal reads `load_portal_levels`. Size 9 has only 322 mazes, so 700/150/150 over three sizes (333 each) cannot fit: 600/120/120 does. The saved files are checked against the real test pile by a test.
- **Progress bar (2026-11-24, G9):** workers are other processes, so they report tries through a Manager queue that `run_seeds` drains while it waits (`wait(..., timeout=0.5)`); no queue is made unless a callback is given. Draw in place only when `sys.stdout.isatty()` so logs stay plain. Time left is rough early on (start-up cost counts), so it is shown from the first window but settles after a few. `script -qc` fakes a terminal for a real check.
- **Dropdown groups (2026-11-24, G10):** a new optional field in a message touches five places: the Pydantic model (with a default), `messages.schema.json`, the zod schema (`.default(...)`), the shared samples (a valid one and an invalid one) and the web test constants. Sort each group on its own and join them; one global sort mixes the groups. react-aria sections (`ListBoxSection` and `Header`) give the headings; a small pure helper (`groupOptions`) keeps the grouping testable.
- **Progress line width (2026-11-24, G9):** a line wider than the terminal wraps, and `\\r` only returns to the start of the last row, so every redraw leaves leftovers (seen in a half-width pane). Fit the line to `shutil.get_terminal_size().columns - 1`: shorten the bar first, cut the text last.
- **Results table (2026-11-24, G11):** the old `finished`, `steps` and `path` columns came from the last 10 training tries, a different brain from the saved one, and all seeds play the same mazes in the same order, so failed tries gave the same step count for every seed. Show numbers of the brain that is exported. Do not import a function named `test_*` into a test module (pytest collects it as a test).
- **Attempt log (2026-11-24, G12):** the page already knows every square of a run (trail plus current square), so the log needed no server change; save a compact path (a list of [x, y]) and build the readable file (step, move, time) only when downloading. Keep paths only on the newest 30 attempts so localStorage stays small, and let older saved attempts load without one.
- **Example configs (2026-11-24, G13):** the first mixed-size example copied the old small recipe and collapsed; an example is a recipe, so start from the best known settings (R3 in `dqn-learning-brain.json`) and check the research notes before writing one.
- **One change per run (2026-11-24, G14):** the wide example keeps the R3 recipe and changes only the mazes (sizes up to 21), so a result can be traced to that change. R3 on sizes 9 to 13 reached 93 to 95% validation with no collapse; the old recipe on the same mazes collapsed.
- **Stop and stuck (2026-11-24, G15):** a client-only status (`stopped`) stays out of the server contract: the page has its own `AttemptStatus` (server statuses plus `stopped`) and the shared samples list `stopped` as an invalid server status. After a stop, a tick can still arrive, so the run reducer ignores every message once the phase is done. Stuck means no new square for 100 steps; a level whose step limit is under 100 times out first, so only big levels can end as stuck.
- **Loader and icons (2026-11-24, G16):** a local upload takes milliseconds, so hold a loading animation for a minimum time (`atLeast(work, ms)`, also on failure) or it only flashes. A liquid fill is a grey copy of the drawing under a colour copy shown through a `<mask>` whose wave path slides up (CSS keyframes); check it by screenshotting paused frames in headless Chromium. A found icon has a licence: Twemoji is CC-BY 4.0, so the credit is in README.md.
- **History page (2026-11-24, G17):** two pages share one attempts list kept in `App`; the Arena stays mounted but `hidden` so a run is not lost when you open History, and `[hidden]` needs `display: none !important` because layout classes set `display`. Hash routing (`#history`) is enough for two pages: no router dependency. A page that promises a download per row needs the data kept for those rows (paths now for 100 attempts, about 5 to 18 KB each).
- **Overlay (2026-11-24, G18):** a fixed full-screen layer with a centred card (`position: fixed; inset: 0; display: grid; place-items: center`) blocks clicks on the page behind it and needs no library. A screenshot taken at the start of a fade-in shows a pale card: wait for the animation, or judge the layout, not the opacity.
- **Divergence (2026-11-24, G19):** on mazes up to 21x21 the shaped DQN learned (71 to 82% wins) and then diverged: reward per try grew from about -16 to -145, the loss went from 0.01 into the thousands and wins fell to 0% in every seed. The loss rises before the wins fall, so watch it. Huber loss and gradient clipping (10) were already on; the next guesses are a lower learning rate and a slower target network. The early stop (patience 8) saved about 12 minutes per run, and best-on-validation kept the good brain.
- **Say what a number is out of (2026-11-24, G20):** "saved at try 1250" confused the CEO until it read "1250 of 3250" with a one-line reason under the table. A column that names a moment needs its scale and its rule in the output, not only in the docs.
- **Drop a column that repeats others (2026-11-24, G21):** the average steps per test maze mix finished mazes with failed ones (a failed maze counts its full step limit), so they mostly repeat the test score; the path ratio (finished mazes only) says more. Keep what a reader can act on in the table and the rest in `summary.json`.
- **The bundle is built after the graph (2026-11-24, G22):** train() returns before training.png is drawn, so the CLI and run_seeds build the bundle after the plot. Read untrusted tars into memory with limits and an allow-list of flat names; never extract to disk.
- **Compare like with like (2026-11-24, G26):** two brains are comparable only when their exam mazes are the same (sizes, maze seed, exam count, exit rule). The Brains page keys the trend on that and warns in the compare; a score from the narrow run (9 to 13) says nothing next to the wide run (9 to 21).
- **Do not store what a batch already says (2026-11-25, G27):** Run all levels plays the same seeds as a manual run, so saving every manual run repeated rows the batch already had. Before adding a record, ask what a reader learns from it that no other record gives. A manual run is for watching.
- **A shadcn block overwrites your components (2026-11-25):** `shadcn add dashboard-01 --overwrite` replaced the Badge, Button and Select I had edited (the green and amber badge colours were lost) and wrote `from "cn"` imports that installed a wrong npm package. After a block, diff the files it replaced and run the typecheck.
